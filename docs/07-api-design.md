# 07 — API Design

> **Status:** Approved · **Owner:** Solution Architecture · **Last updated:** 2026-09-11

The backend exposes **one public REST API** consumed by the website, the admin
portal and the mobile app. There is no client-specific API — differences are
handled by field selection and pagination, not by forking the contract.

**Base URL:** `https://api.medichain.example/api/v1`
**Contract:** OpenAPI 3.1, generated from decorators, published at `/docs`.

---

## 1. Principles

| Principle | Rule |
|---|---|
| Contract first | The OpenAPI spec is the interface. Clients are generated from it, never hand-written. |
| Resource-oriented | URLs name nouns; HTTP verbs carry the action. |
| Stateless | Every request carries its own auth. No server-side session affinity. |
| Idempotent where it must be | All unsafe writes accept `Idempotency-Key`. |
| Explicit versioning | `/api/v1` in the path. Additive changes only within a version. |
| Consistent envelope | One success shape, one error shape, everywhere. |
| Bounded by default | Every list endpoint is paginated. No unbounded query can be issued. |
| Observable | Every response carries `X-Correlation-Id` and `X-Request-Id`. |
| Secure by default | Auth required unless explicitly marked public. |

---

## 2. Versioning and compatibility

```
/api/v1/orders
/api/v1/catalog/products
/api/v2/orders          ← only when a breaking change is unavoidable
```

**Allowed within a version (non-breaking):**
- Adding a new endpoint
- Adding an **optional** request field
- Adding a response field
- Adding a new enum value *only* if clients are documented to ignore unknown values

**Requires a new version:**
- Removing or renaming a field
- Changing a field's type or nullability
- Making an optional field required
- Changing default behaviour or semantics
- Removing an enum value

**Deprecation process:** an endpoint to be retired returns `Deprecation: true`,
`Sunset: <http-date>` and a `Link: <successor>; rel="successor-version"` header for
at least **6 months** before removal. Mobile clients cannot be force-updated, so the
window is deliberately long.

**Minimum client version gate:**

```
X-App-Version: 2.3.1
X-App-Platform: ios
```

If the version is below the configured minimum, the API returns `426 Upgrade Required`
with a structured body the app renders as a blocking upgrade screen. This is the only
reliable way to retire an old mobile client.

## 3. Authentication

| Mechanism | Use |
|---|---|
| `Authorization: Bearer <access_token>` | All client requests |
| `X-Api-Key` | Server-to-server (buyer ERP integration), phase 4 |
| Refresh token (body) | `POST /auth/refresh` only |

**Token policy**

| Token | TTL | Storage (client) | Rotation |
|---|---|---|---|
| Access (JWT) | 15 min | Memory only | — |
| Refresh | 30 days | HttpOnly cookie (web) / Keychain (mobile) | Rotated on every use |

The access token is a JWT signed with HS256 (RS256 if we ever need third-party
verification). Claims:

```jsonc
{
  "sub": "user-uuid",
  "tid": "tenant-uuid",
  "oid": "organisation-uuid",
  "roles": ["BUYER_ADMIN"],
  "caps": ["order:create", "order:read"],
  "scp": { "warehouses": ["..."], "regions": ["..."] },
  "sid": "session-uuid",
  "iat": 1757500000,
  "exp": 1757500900,
  "iss": "medichain",
  "aud": "medichain-api"
}
```

**Deliberate design choice:** capabilities are embedded in the token for fast
authorisation, but **never trusted alone**. A permission change takes effect
immediately because the guard re-checks against a Redis-cached permission set keyed
by `sid`. Embedding without re-checking would mean a revoked user keeps access for
up to 15 minutes.

## 4. Request conventions

### 4.1 Headers

| Header | Required | Purpose |
|---|---|---|
| `Authorization` | Yes (except public routes) | Bearer token |
| `Content-Type` | On writes | `application/json` |
| `Accept-Language` | No | `en` \| `hi` — response messages and content |
| `X-Correlation-Id` | No | Client-supplied trace id; generated if absent |
| `X-Request-Id` | No | Generated by the LB if absent |
| `Idempotency-Key` | Yes on unsafe writes | UUID, unique per logical operation |
| `X-App-Version` / `X-App-Platform` | Mobile | Version gate |
| `If-Match` | Optional | Optimistic concurrency (`ETag`) |

### 4.2 Pagination

**Offset pagination** — default for admin lists where page numbers matter:

```http
GET /api/v1/orders?page=1&pageSize=25&sort=-placedAt
```

```jsonc
{
  "data": [ /* ... */ ],
  "meta": {
    "page": 1,
    "pageSize": 25,
    "total": 1843,
    "totalPages": 74,
    "hasNext": true,
    "hasPrev": false
  }
}
```

**Cursor pagination** — for large, fast-moving, or infinite-scroll lists:

```http
GET /api/v1/catalog/products?limit=50&cursor=eyJpZCI6Ii4uLiJ9
```

```jsonc
{
  "data": [ /* ... */ ],
  "meta": { "limit": 50, "nextCursor": "eyJpZCI6Ii4uLiJ9", "hasNext": true }
}
```

**Rules**
- `pageSize` / `limit` is capped at 100 server-side. A larger value is clamped, not
  rejected, and `meta.pageSize` reflects the applied value.
- Default sort is always deterministic and always includes a tiebreaker
  (`-placedAt, id`) so pagination never duplicates or skips rows.
- `total` is omitted on cursor-paginated endpoints — counting is expensive and the
  client does not need it.

### 4.3 Filtering and sorting

```
?status=CONFIRMED,DISPATCHED          # comma = OR
&organisationId=<uuid>                # equality
&placedAtFrom=2026-09-01              # range: From / To suffix
&minTotal=1000&maxTotal=50000         # numeric range
&q=paracetamol                        # free-text (only where documented)
&include=lines,shipments              # sparse expansion
&fields=id,orderNo,grandTotal,status  # sparse fieldset
&sort=-placedAt,grandTotal            # '-' = descending
```

Filter parameters are **allow-listed per endpoint**. An unknown filter is a `400`,
not a silently ignored parameter — a silently ignored filter means a user believes
they are looking at a subset when they are looking at everything.

### 4.4 Body conventions

| Concern | Convention |
|---|---|
| Field naming | `camelCase` in JSON |
| Money | **Decimal string** — `"1234.5600"`, never a number |
| Quantity | Decimal string — `"10.0000"` |
| Dates | `date` → `"2026-09-11"`; timestamps → ISO 8601 UTC `"2026-09-11T09:30:00Z"` |
| IDs | UUID strings |
| Enums | `SCREAMING_SNAKE_CASE` strings |
| Null vs absent | `null` means "explicitly cleared"; absent means "not provided, leave unchanged" |

**Why money is a string:** JSON numbers are IEEE-754 doubles in virtually every
parser. `0.1 + 0.2 !== 0.3` is not a curiosity when you are invoicing 40,000 lines a
month — it is a reconciliation failure. Strings force the client to use a decimal
library, which is the correct behaviour.

## 5. Response conventions

### 5.1 Success

Single resource — the resource, unwrapped:

```jsonc
GET /api/v1/orders/8f3c...

{
  "id": "8f3c...",
  "orderNo": "INV-2026-000412",
  "status": "CONFIRMED",
  "organisation": { "id": "...", "legalName": "Sunrise Pharma Distributors" },
  "grandTotal": "148250.0000",
  "currency": "INR",
  "placedAt": "2026-09-11T09:30:00Z",
  "lines": [ /* ... */ ]
}
```

Collection — wrapped in `data` + `meta` (see pagination above).

Mutations — the affected resource plus a message:

```jsonc
POST /api/v1/orders        → 201 Created

{
  "data": { "id": "8f3c...", "orderNo": "SO-2026-000412", "status": "PLACED" },
  "message": "Order placed successfully"
}
```

### 5.2 Errors — RFC 9457 `application/problem+json`

```jsonc
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/problem+json

{
  "type": "https://api.medichain.example/problems/insufficient-credit",
  "title": "Insufficient credit limit",
  "status": 422,
  "detail": "Order total 148250.0000 exceeds available credit 95000.0000.",
  "instance": "/api/v1/orders",
  "correlationId": "01J8X2...",
  "timestamp": "2026-09-11T09:30:00Z",
  "errors": [
    {
      "field": "grandTotal",
      "code": "CREDIT_LIMIT_EXCEEDED",
      "message": "Available credit: 95000.0000",
      "meta": { "available": "95000.0000", "required": "148250.0000" }
    }
  ]
}
```

**One shape, always.** Clients have exactly one error parser. `errors[]` is present
for validation failures and omitted otherwise.

### 5.3 Status code map

| Code | When |
|---|---|
| 200 | Successful read or update |
| 201 | Resource created |
| 202 | Accepted for async processing |
| 204 | Successful delete / no body |
| 400 | Malformed request |
| 401 | Missing or invalid credentials |
| 403 | Authenticated but not permitted |
| 404 | Not found **or** not visible to this tenant |
| 409 | Conflict — duplicate, state conflict, idempotency mismatch |
| 422 | Business rule violation (valid syntax, invalid semantics) |
| 426 | Client version too old |
| 428 | `If-Match` required |
| 429 | Rate limited |
| 500 | Unhandled server error |
| 503 | Dependency down — **readiness and degraded modes** |

**`404` vs `403`:** a resource belonging to another tenant returns `404`, never
`403`. Returning `403` confirms the resource exists, which is an information leak.

## 6. Idempotency

Every `POST`, `PATCH`, `PUT`, `DELETE` accepts `Idempotency-Key`.

```
POST /api/v1/orders
Idempotency-Key: 7c9e6679-7425-40de-944b-e07fc1f90ae7
```

| Situation | Response |
|---|---|
| First request, in flight | Execute; store the response |
| Same key + same body hash, completed | **Replay** the stored response, `Idempotency-Replayed: true` |
| Same key + different body hash | `409 Conflict`, code `IDEMPOTENCY_KEY_REUSED` |
| Same key, still in flight | `409 Conflict` + `Retry-After: 1` |

Records expire after 24 hours. The key is scoped per endpoint
(`scope = "POST /api/v1/orders"`), so the same UUID on a different endpoint is a
different operation.

**This is the primary defence against duplicate orders and double-credited payments.**
Mobile clients on flaky networks retry aggressively; without idempotency, that
becomes duplicate orders in production.

## 7. Rate limiting

Enforced in the app layer with a Redis sliding window. Response headers on every
response:

```
RateLimit-Limit: 300
RateLimit-Remaining: 287
RateLimit-Reset: 42
```

On breach: `429` with `Retry-After: 42` and problem+json `type` = `.../rate-limited`.

| Scope | Limit | Notes |
|---|---|---|
| Anonymous, per IP | 60 / min | |
| Authenticated, per principal | 300 / min | |
| `POST /auth/login`, `/auth/otp` | 10 / min | Per IP **and** per username |
| `GET /catalog/search` | 120 / min | Search is the most expensive read |
| Export endpoints | 5 / hour | Runs as a background job |
| `POST /orders` | 60 / min | Higher than typical, to allow legitimate bulk entry |

**Fail-open policy:** if Redis is unreachable, the limiter logs an error and allows
the request. The WAF still enforces a coarse per-IP limit. Availability beats
precise rate limiting during a cache outage.

| Method | Path | Notes |
|---|---|---|
| 🔒 POST | `/files/upload-url` | Pre-signed S3 PUT |
| 🔒 GET | `/files/:id/download-url` | Pre-signed, short TTL |

**Direct-to-S3 uploads.** Files never pass through the API process. The API issues a
pre-signed URL with a size and content-type constraint; the client uploads directly
to object storage; the API then confirms and virus-scans. This keeps the API pods
free of large payloads, which is what makes horizontal scaling cheap.

## 9. Real-time and webhooks

### 9.1 Server → client

| Mechanism | Use |
|---|---|
| **SSE** `GET /events/stream` | Order status, notification badge, stock alerts — one-way, auto-reconnect, works everywhere |
| **Web Push** | Mobile background notifications |
| **Polling** | Fallback; TanStack Query refetch interval |

SSE is chosen over WebSocket because every real-time need here is one-directional.
WebSocket adds bidirectional complexity and connection-affinity problems that a
stateless tier does not want.

### 9.2 Outbound webhooks (phase 4)

Buyers' ERPs can subscribe to events. Each delivery is signed:

```
X-MediChain-Signature: t=1757500000,v1=<hmac-sha256(t + "." + body)>
X-MediChain-Event: order.dispatched
X-MediChain-Delivery: <uuid>
```

Retry policy: 5 attempts with exponential backoff (1 m, 5 m, 30 m, 2 h, 12 h), then
dead-letter with an admin alert. Delivery attempts are visible in the admin portal.

## 10. Contract testing and client generation

```bash
pnpm --filter @medichain/backend openapi:generate   # → openapi.json
pnpm --filter @medichain/api-client generate        # → typed client
```

**CI gates**

- A breaking-change detector diffs `openapi.json` against `main`. A breaking change
  fails the build unless it is accompanied by a version bump and an approval label.
- Contract tests (Pact-style) verify the website, admin and mobile clients against
  the published spec.
- The generated client is committed, so a contract change is always visible in a diff.

**Why generate rather than hand-write:** a hand-written client drifts from the
server the moment someone forgets to update it, and the failure surfaces as a
runtime `undefined` in production rather than a compile error.
